## 总体评价（200 字以内）

项目已具备限定只读场景的可用 Alpha 基础。身份、消息、控制与派发意图共用 SQLite 事务，未知执行保守对账，这些复杂度有实际价值。主要短板在外部 Runtime 的证据认领与成本归属：本轮修复了原生 Turn 误认领和 UTF-8 静默损坏，另确认人工结算与后续累计通知可能重复记账。当前不宜宣称生产级恢复或精确费用核算。

R1 通过替身 Runtime 精确复现事件顺序和越权工具效果；没有测量真实多客户端竞争的发生概率。它不是对同一 OS 用户任意宿主代码的隔离承诺：该用户本来就能操作数据库和原生 daemon。

### R3 的复现与为什么暂不改账本

```sh
node scripts/diagnostics/usage-gap.ts
```

该诊断应当以非零退出，当前断言为 `95 !== 75`。脚本只创建和删除自己的临时业务 DB，不调用模型。它是**公开保留的失败门槛**，没有改成断言错误结果，也没有混入通过数。

原有回归在人工结算后先补发了前一 Turn 的最终通知 50，再发送下一 Turn 累计 75，因此没有覆盖“最终通知永久缺失”的分支。本轮没有削弱那个正确用例。

根因是两个不同来源叠加：人工收据已经增加 charged，而原生游标仍是 30；后续差值 45 再次包含已人工补足的 20。简单推进原生游标会篡改观测来源；简单抵扣又不能处理 observe 模式下后续 Turn 已结算、再人工补记旧 Turn 的情况。后一种情况还涉及既有用量在多个 Attempt 间的重新归属。

最小可靠方向应先明确：**Thread 累计事实、人工最终收据和 Attempt 归属分别保留，结算记录必须描述其与累计事实的覆盖关系。** 唯一归属不可证明时保留 unknown，并把树级已知累计量与未归属责任分开展示；不能把所有缺口都算给下一个 Turn。至少补齐“收据先/后于下一次用量、多个缺失 Turn、迟到/重复/乱序通知、两种策略、重启及旧记录迁移”的矩阵。

这将改变持久账本和既有结算合同，可能需要迁移；遵循本轮“不擅自实施重大架构或不兼容变更”的边界，当前只保留失败诊断和设计分析。**本轮审查没有全绿，也未据此发布新 Release。** 实际账单或硬预算决策不能只依赖存在该缺口的 spent。

## 已完成优化与验证

1. **认领需要证据**：started 通知不再等同于本地 start 回复。ACK 之前仅在历史中存在匹配 Turn ID 和本地 attempt marker 时认领；否则暂时隔离。后来的 ACK 或历史证据只解除它确实证明属于本地的隔离，真正外来 Turn 不随之放行。覆盖有效 marker、空历史、不可读历史、延迟 ACK、外来工具调用、外来完成通知，以及查证期间连接失效的旧回调。旧版可能已经误记的历史记录不在本轮自动改写。
2. **控制通道双向流式 UTF-8 解码**：使用 socket 自带解码器，保留原有帧限额、认证和幂等键。不调整消息状态或正文限制。
3. **事件定位使用现有索引**：[Store.attemptForTurn](../src/storage/store.ts) L960 替代每次载入全部历史后 `.find()`。复用现有 `native_turn(thread_id,turn_id)` 唯一索引，不增加表、迁移或缓存。

可复验的查找微基准：

```sh
node scripts/diagnostics/lookup-benchmark.ts
```

隔离 DB，5000 条历史，每条输入 2000 字符，各路径采样 25 次取中位数。本机一次实测：全量载入查找 **47.75 ms**，索引定位 **0.022 ms**；查询计划确认命中 native_turn。这只证明该合成历史下的查找收益，不是端到端加速倍数、真实规模预测或 token 节省证明。

## 架构判断

### 六个维度

| 维度 | 判断 |
| --- | --- |
| 正确性 | active Attempt 唯一索引、事务内准入、CAS 与键去重可靠；R1 已补认领证据缺口。R3 仍破坏成本归属。 |
| 可靠性 | 正常退出、SIGKILL、丢回复、旧连接与不完整历史已有针对性测试。持久 unknown 是正确结果，不是自动恢复成功；历史缺失时无法保证自动完成。 |
| 安全性 | 身份从实际 Thread/Turn 派生，模型不能传父节点/发送者、跨树控制或清除人工 fence。只适合同一凭据/信任域；本机操作者不是对抗性租户边界。 |
| 性能 | 原全历史事件查找可明确消除；完整 status/list 仍载入大量历史正文。全局串行 tick 在慢 RPC 时可能形成队首等待，尚无生产延迟分布，未据此并行化派发。 |
| 可维护性 | 大 Store 维持跨域事务有理由；为了行数拆成多个独立 Repository 反而容易破坏原子性。最应集中的是成本证据与归属规则，其次是重复的状态投影查询。 |
| 实际价值 | 控制平面验证充分于“能协作”，不足于证明比单 Agent 更好、更省。7×6 验收证明递归链路，不证明业务价值。 |

### 组件是否必要

| 组件 | 实际必要性、替代方案与维护判断 |
| --- | --- |
| Coordinator | 原生执行仍由 daemon 持有；本层把派发意图、控制、业务消息和配额联系起来。直接删掉会失去跨重启的调度与根节点唤醒合同。单写者适合当前单机范围，无需上分布式队列。 |
| Agent / Thread / Attempt | 业务身份与上下文分离支持重绑和审计；Attempt 是派发意图，不是另一个模型循环。合并会丢失 ACK 缺失、连接代际及未派发状态。代际 fence 不能为了简化删除。 |
| 消息系统 | 业务 SQLite 的 queued/投递/显式确认与控制共用事务；直接调用 turn/start 没有相同的接纳与消费记录。两张人/Agent 消息表有重复读取成本，但保持人的来源与模型身份不同有价值，当前不值得迁移合表。 |
| Task Board | 显式业务完成、owner、依赖和 CAS 的确补足了 processed ≠ 完成。不是每个小任务都需要；应按完成依赖使用，不能强迫所有计算多走一组工具。没有必要扩展成自动 DAG 引擎。 |
| token / 执行配额 | 结构和次数硬限制合理；默认 observe 免去误拦。enforce 是可选业务合同，但账本归属必须先解决 R3，不能将复杂度藏进一个“剩余 token”字段。 |
| Runtime Adapter / transport | 保留固定版本、独立 home、统一超时与不确定返回，避免重写模型循环。现有薄适配足够；没有证据支持为未来 provider 先建庞大插件系统。 |

**结论：没有明显的整体过度设计。** 必要复杂度来自 SQLite 与 Native Runtime 不能共同提交事务，以及派发、消息消费、Task 完成、用量终结是四个不同事实。最值得简化的是重复的读投影和账本中混杂的来源/归属推导，不能删除保守恢复边界。

## 未实施建议（按优先级）

| 优先级 | 建议 | 收益 / 成本 / 风险 | 当前不实施的理由 |
| --- | --- | --- | --- |
| 1 | R3 账本覆盖关系设计与迁移审查 | 高 / 中高 / 高 | 已复现，但可靠修复涉及结算语义与旧数据；不能只为通过单个数字用例更改游标。 |
| 2 | 收窄 managed `agent_list` 的默认输出，完整历史按需读取 | 中高 / 中 / 中 | 当前返回每节点最多 20 个完整结果和 50 条消息。减少上下文有合理收益，但需兼容旧 Thread 工具目录并实测各工作流，不能无提示改返回合同。 |
| 3 | 用代表性任务做单/多 Agent 对照 | 决策价值高 / 中 / 用量风险 | [基准方案](benchmark-plan.md)已定义，未获大规模模型实验确认，故未执行。 |
| 4 | 长历史与 Task tombstone 的查询/保留策略 | 中 / 中 / 中 | live Task 限 256 不等于 tombstone 总量有界；当前 rows() 会计算全历史投影。无真实保留规模数据，先量化再归档，不能删除审计。 |
| 5 | 慢 RPC 下的调度公平性、自动重连与长 Turn 期限 | 场景相关 / 中高 / 高 | 当前 event-driven 单队列容易理解；并发化或自动重试必须重新证明单 Attempt/原生接纳不重放，不以理论吞吐取代正确性。 |

尚未复现的风险包括：异常协议包和慢磁盘组合、daemon 更换版本后的历史完整性、超长单 Turn 内反复工具调用的资源占用。源码没有整个 Turn 的墙钟期限，结构次数不等于单 Turn 用量硬上限；这是当前能力边界，不冒充新 Bug。

GUI、跨机器调度、多凭据隔离、并行写仓库/合并和自动 DAG 执行仍不属于这个只读 Alpha 的目标，不作为缺陷计数。旧审查的超限队首行、processed 语义和保守空历史问题已有修复或明确合同，本轮没有重复记成新发现。

### 下一阶段最值得投入的三项工作

1. 先完成 R3 的账本覆盖关系与旧数据迁移方案，扩大跨 Turn 故障矩阵。
2. 建立固定版本的协议契约与故障回放门槛，把外来/迟到/部分历史纳入每次适配器升级验收。
3. 执行经确认的小规模代表性对照，再决定输出精简、任务粒度和递归深度；不要先开发 GUI 或更多编排层。

当前最大的技术风险仍是**把跨状态域的间接证据当成直接事实**。R1 是执行认领的例子，R3 是用量归属的例子；本地事务完整性无法替代这两种证据合同。

## 依据与边界

官方 [App Server 文档](https://learn.chatgpt.com/docs/app-server)说明 started 通知的 items 为空，并分别列出 Turn 与 usage 通知；它没有提供“收到 started 就证明属于当前请求”的保证。本机精确版本生成的 `Turn` 类型也没有可直接补齐缺失最终用量的字段。本轮以固定 CLI 生成的协议类型、本项目实际代码、故障注入和真实单 Turn 验证为准，不把当前在线文档直接当作旧版本的完整合同。
